# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Boord Packhouse covers everything that happens to fruit after Boord Receiving checks a load in, up to the moment a pallet or juice bin leaves on a truck. `Boord_Packhouse_App_Plan.md` is the plan: the fruit's routes, the roles, the data model and the build stages. It follows the **Boord Labour** pattern (`../Boord-labour`):

- its own uvicorn process on port **8060**, bound to 127.0.0.1 and published only via `tailscale serve --https=8060`;
- its own SQLite `data/packhouse.db`;
- Boord's `boord.db` opened **read-only** for workers, blocks, suppliers and received lots. `boord.py` holds every query as plain SQL (never SQLModel mirrors, so Boord's tables stay out of our Alembic metadata), and `boord.BOORD_SCHEMA_CHECK` lists every column read: `main._wait_for_boord` refuses to boot if one disappears. Change the two together.

Access has two layers:
- **Tailscale** gets you to the app at all. It binds 127.0.0.1; never bind 0.0.0.0.
- **The 4-digit settings PIN** separates Settings (and later corrections and overrides) from the floor screens, which have no login; who did what will be a Boord badge scan.
  - **Every settings endpoint must depend on `admin_auth.require_admin`**, which checks the `packhouse_admin` cookie. The floor endpoints stay open: `/api/version`, `/api/weather/current`, `/api/workers`, `/api/fruit-sources`, `/api/tents`, `/api/baths`, `/api/packaging`, `/api/markets`, `/api/suppliers`, `/api/sulfur/*`, `/api/acid/*`, `/api/consignment/*`, `/api/juice/*`, `/api/deliverynote/*` (its PDF included).
  - The PIN is exactly 4 digits, pbkdf2-hashed in `data/admin_pin.txt`, and set only from the server console (`backend/set_pin.py`, also run by `install.ps1`), never via the web. Five wrong tries lock it for 5 minutes.
  - Unlike Labour's admin phone, the tablets are shared: the cookie is a session cookie, and `app.js` signs out when Settings is left, after 5 idle minutes, and on every page load.
  - In tests, use the `admin_client` fixture for settings endpoints. The TestClient runs on https because the cookie is Secure.

**How they depend on each other:**
- **Boord is the hub.** Its `data/boord.db` is opened read-only by Owner (harvest, lots, blocks, suppliers), Labour (the worker register, and Boord's `data/photos` for faces), Monitor (tablet station, last sync and outbox) and Packhouse (received lots, blocks, suppliers, workers).
  - Boord is that database's only writer and migrates it at startup.
  - Owner, Labour and Packhouse refuse to boot if a column they read disappears. A Boord migration that drops or renames a column needs those apps updated in step.
- **Owner also reads Packhouse.** For the Dashboard's Delivered vs Picked card, Owner opens Packhouse's `data/packhouse.db` read-only, the same way Boord's own admin dashboard does (delivery notes are Packhouse's data, not Boord's). Optional: missing or unreadable just drops that one figure.
- **Labour's badges are Boord's.** The badge QR holds exactly `worker.id` (`Boord/frontend/admin/print-badge.html`), and Labour and Packhouse vendor Boord's `frontend/shared/`.
- **Owner asks Notes.** The "Ask the farm notes" bridge calls Notes' `/api/ai/ask` at `OWNER_NOTES_URL` (`http://127.0.0.1:8020`) and can share Notes' `data/anthropic_key.txt`.
- **Monitor keeps the others running.** Since Monitor 2.0 its `watchdog.ps1` (restarts an app that stops answering) and `heartbeat.ps1` (pings healthchecks.io) cover all seven, as the scheduled tasks "Boord Watchdog" and "Boord Heartbeat". Until then they lived in Boord's repo; Boord's copies are now forwarders to Monitor's.
  - **The app table is Monitor's `apps.json`, the one copy.** Monitor's `backend/apps.py`, `watchdog.ps1` and `heartbeat.ps1` all read it. Adding or moving an app is one line there plus the port table above; the `tailscale serve` ports are also in Boord's MANUAL.md.
  - The watchdog stands down while any app's updater (its `updater` in `apps.json`) or an installer runs, and its `-Restart "<Name>"` is what Monitor's Restart button runs. It exits 2 when it stands down.
- **Monitor watches everything.** It shows each app's up/down state and `/api/version`, Tailscale and the PC, keeps uptime history, SLOs and incidents, and pushes an alert after three failed checks in a row.
  - Every app's `/api/version` keeps the same field names (`tag`, `state`, `frontend_version`), because Monitor and the heartbeat read them all.
  - An off-site copy of the monitor on the owner's Mac alerts when the whole farm PC is unreachable.
- **Kudde and Notes stand alone.** No other app reads their data. They are only watched and restarted.

**What they share by convention, not code:**
- One release key: fingerprint `67C64CFDD584DD140E58AF6E329C9B9DD0562A9D` in each app's `data\release_key.fpr`.
- Releases are signed tags, made from an up-to-date `main` on the Mac and installed by each app's updater on the farm PC.
- `stop_server.ps1` stops each server, never a bare `schtasks /end`. Labour's copy is the reference.
- Each installer adds a Git `safe.directory` exception so SYSTEM's Git can read the repo folder.
- Python 3.9-compatible code, plain JS with no CDNs (the phones are tailnet-only), and `VERSION` plus the service-worker `CACHE` bumped with every frontend change.
- Fixes to the copied deployment files (`install.ps1`, the updaters, `stop_server.ps1`, `release.sh`) flow between the repos.

## Architecture

- **Home screen** (`frontend/index.html`, `app.js`): a grid of big icons, one per role (`MODULES` in app.js). Sulfur tent and Acid bath are `parked` (in `MODULES` and `SETTINGS_PAGES`): off the home screen and the settings menu until the farm takes them up again, their code untouched and `#sulfur` / `#acid` still working; remove the flag to bring one back. A role opens full screen at `#<id>`. The bottom menu has Pallets, Delivery, Juice (each greyed out on its own screen) and Settings (behind the PIN keypad); the home grid is reached from Settings' Home. Once the PIN is in, Settings swaps in its own bottom menu: Home (which signs Settings out) and one button per page in `SETTINGS_PAGES` (app.js), at `#settings/<id>`: Sulfur (the tents, then the suggested-time and SO₂ numbers) Acid (the baths), Pallet Stack (the packs and markets), Delivery Note (the transporters, receivers, the last note number and the cooled-to) and Setup (backups and the settings PIN). One page per role; Setup is for looking after the app itself. A new settings page is an entry there plus a `<div data-settings-page="<id>">` in index.html; its `load` runs each time it opens. Every role is a placeholder until its build stage lands.
- **Header:** the weather strip comes from `GET /api/weather/current`, which passes Boord's own `/api/weather/current` through from `BOORD_URL` (default `http://127.0.0.1:8000`). Boord owns the source (iWeathar station or GPS in Boord's Settings) and its cache; an unreachable Boord is `{}`, never an error. The sync pill uses Field's colours; today it only probes `/api/version`, and gains the outbox count when the first module queues records.
- **Backups** (`backend/backup.py`, Boord's backup.py trimmed by way of Labour's): at 02:00 every night, when `packhouse.db` changed since the last archive (hash of a SQLite-API snapshot), it writes `data/backups/packhouse_backup_*.zip` and keeps the newest 14. Settings -> Setup has Backup Now (always writes one), the list and Download, all behind `require_admin`. Off-site copies go to the folder in **Boord's** `data/backup_copy_to.txt`. The pruner only matches `packhouse_backup_*.zip`, so the updater's `packhouse-before-*.db` copies are never touched.
- **Schema:** Alembic (`migrate.py`, `migrations/`, Boord's setup trimmed: there is no pre-Alembic database to adopt). `db.init_packhouse_db()` runs it at startup and in the updater. Every change to `models.py` needs a migration: `cd backend && .venv/bin/python -m alembic revision --autogenerate -m "what changed"`, using `batch_alter_table` for SQLite.
- **Offline-first floor** (`frontend/sync.js`, `idb.js`): packhouse Wi-Fi is patchy. Workers, tents, fruit sources and the server's runs are cached in localStorage; a run started or ended on a tablet goes into the IndexedDB outbox first and is sent by `POST /api/sulfur/sync`, an idempotent upsert by the tablet-made uuid where ending is one-way. Every sulfur response carries `server_now`, and `Store.now()` is the tablet clock corrected by it: use it, never `Date.now()`, for anything a run stores. The pill shows Field's states (synced / Syncing N / Offline - N pending).
- **Sulfur tent** (`frontend/sulfur.js`, `routers/sulfur.py`, `routers/tents.py`): opens with a Boord badge scan (the QR is `worker.id`, looked up in the cached worker list, so it works offline); the operator stays signed in until 15 idle minutes on a badge-scanned screen (any tap, key or scroll there counts, and so does coming back to one: app.js), or 10 minutes after leaving it (a grace period, so a trip to Home needs no rescan); "Not you?" signs out at once. One card per active tent (Settings -> Sulfur, retired never deleted). A run records grams, minutes, crates and either a block or a supplier (`boord.fruit_sources`: today's receipts, then the last earlier receiving day, farm-local days; pre-selected only when today has exactly one). Countdowns run on the tablet; overdue runs sound an alarm on the sulfur and home screens, and the screen is kept awake while any tent runs. Weather is stamped by the server only on a run that arrives within 10 minutes of its start.
- **Batch, size and report:** every run gets a `batch_no` on the tablet (`batchNo` in `suggest.js`: `T2-4104-1057-B15/8a-K7` = tent id, date code (ISO week last digit, weekday, 0, week first digit: Monday of week 44 is 4104), farm-local time, the blocks (`S<id>` for a bought-in supplier) and two characters of the uuid) and a `size` picked from Settings -> Sulfur's list (`SulfurSettings.sizes`; this tablet's last choice comes up chosen, and Start needs one). A load may hold a second block: the first source stays in `block_id`/`supplier_id` (the acid dip copies only that one), the rest are the JSON list `more_sources`. A tent's card starts with the grams its latest run used (this tablet's runs, then `last_grams` from `GET /api/tents`, then the tent default), and editing grams or crates lets the time follow the suggestion again. Settings -> Sulfur has the daily report (`routers/sulfur_report.py`, behind the PIN): the paper sulfur-room log and usage-per-day sheet as a table, `/xlsx` (openpyxl) and `/pdf` (fpdf2, latin-1 text only), by farm-local day and tent with a total per day.
- **Suggested time** (`frontend/suggest.js`, settings in `models.SulfurSettings`, edited in Settings -> Sulfur): there is no published formula for litchi sulfur time, so this is a transparent starting rule the farm tunes, never a "scientific" answer. The tent's default minutes is its time at the reference conditions (425 g, 24 crates of 20 kg, 25 °C, 60 %); it is scaled by fruit per gram (crates × Settings' packhouse crate weight, ~20 kg: after sorting the fruit is repacked into 20 kg crates for the tents, so Boord's ~7 kg field-crate weights and counts must never be used for a tent load; the fruit list labels Boord's counts "field crates"), the weather (the header's last reading, cached), and a per-variety factor, then rounded and clamped. It runs on the tablet so it works offline; the card shows each step, follows the suggestion until the operator steps the time, and the run stores `suggested_minutes`, `fruit_kg` and the weather used beside the chosen `minutes`, for tuning later. `node frontend/suggest_check.js` (also run by `tests/test_suggest.py`) checks it.
- **Acid bath** (`frontend/acid.js`, `routers/acid.py`, `routers/baths.py`): the sulfur tent's technique, step for step. It opens with the same badge scan and `Operator`; each bath (Settings -> Acid, seeded Bath 1 and 2, retired never deleted) is a card. Batches, chemical changes and concentration checks are made on the tablet with a uuid, queued in the same IndexedDB outbox (`kind` = `acid_batch` / `acid_change` / `acid_check`; sulfur runs have none) and sent by `POST /api/acid/sync`, an idempotent upsert where each stage of a batch (dip ended, done) is one-way. A batch is dipping -> drying -> done; a dip left in sounds the alarm, drying only says ready to pack. Export batches are picked from finished sulfur runs not yet dipped (`sulfur_run_uuid`, its block or supplier and crates copied in); local batches come straight from the fruit sources. Bath health (days and crates since the last change, due at `Bath.change_days` / `change_crates`: the SOP's two changes a week, 500 crates): the server sums the crates since its latest change (`/api/acid/state`'s `health`, so it never sends a bath's whole history: batches are only those still going or from the last 24 h), and the tablet adds its own batches the server hasn't had; a change made on the tablet and not yet sent restarts the count locally. Nothing yet stops a sulfur run being dipped twice by hand: the picker only hides runs already used, by this tablet or by any batch in the last 4 days (`used_runs`, retired baths included).
- **Consignment, shown as "Pallet Stack"** (`frontend/consignment.js`, `routers/consignment.py`, `routers/consignment_settings.py`): the paper consignment sheet, made on a **phone**, at `#palletstack` (its settings at `#settings/palletstack`; the code and records keep the name consignment). It opens with the sulfur screen's badge scan and `Operator` (same idle and grace sign-out, its own operator bar), or with the settings PIN instead (Use the PIN instead, on Pallet Stack and Delivery Note only: `PIN_OPENS` and `askPin` in app.js, checked by `POST /api/admin/check`, the same PIN and lockout but no Settings cookie; the operator is then just "PIN", and it needs the server); a pallet stores `scanned_by`/`scanned_by_name` (set once, by the server on first arrival) and `changed_by`/`changed_by_name` (each save or removal). The screen is Add a new pallet, then Pallets added today, then Pallets this season (`seasonView`: every pallet of the calendar year this phone holds, by market group, each tapped to edit or delete like today's; one whose delivery note was deleted and is on no live note is highlighted amber (to change it, or split it: take cartons off, add a new pallet for them), `freedBy`/`freedTag`, as it is on the delivery note's picker; `Store.allNotes` keeps the deleted notes the server sends) (this phone's day, with the day's totals; a refused pallet shows whatever its day) under a heading per market group, USA, EU and Local, each with its own totals and newest first within it (`marketGroup`, `MARKET_GROUPS` and the heading `groupHead`, a band across the card in the group's colour, blue USA, violet EU, green Local, `GROUP_BAND`, and each pallet or note row under it across the card in a lighter shade of the same colour, a ticked one a shade darker, `groupRow`, live in consignment.js, which loads before deliverynote.js and shares them): each pallet's number, date code, supplier, market and barcode, its cartons and kg in the corner, and its lines numbered 1-n (20 x 1kg XXL, Block 15, Early Delight). There is no list of stacks. A pallet is the code scanned off its label (Html5Qrcode, Code 128 first, the camera opening only when Scan is pressed (again closes it), a code taken only once read twice in a row (`twiceInARow`: one read can be noise, ITF and EAN especially; the seal scan does the same), typing works too; **needed**: a pallet can't be saved without one, on the phone or the server; one saved without it while it was optional, v0.39 to v0.45, shows no barcode line and can still be removed, but needs one to be saved again), its supplier (Boord's `supplier` table by way of `boord.suppliers()`, own farm first, name copied) and market (a new pallet starts with the last one's), and one or more lines (pack, cartons, block). A stack (`Consignment`) only groups pallets, a uuid and a date: a new pallet goes on the newest one, made with the first pallet. Settings -> Consignment holds the **packs** (`Packaging`: name and real `carton_kg`, e.g. Pre-pac 0.48, 1kg XXL 1.1) and the **markets** (`Market`: USA/EU Sea/Air Freight, Local), seeded by the migration, the packs listed lightest carton first, retired by unticking In use and deleted only while no live pallet uses one (409 otherwise: editing that pallet still needs it); a pallet line copies the pack's name and weight so old pallets never change. Kinds `consignment` / `pallet` go through the same outbox to `POST /api/consignment/sync`, but unlike a run both stay **editable**: each save re-queues the whole record (`rev`, so an edit made while it was being sent stays pending) and the server takes the latest copy; `Store.liveMerged` lets an unsent local copy win. Each pallet has a 3-digit `pallet_ref` (the number on the sheet): typed once (or started at 100), then the form offers the highest this season + 1; unique for the season (calendar year scanned) across every stack, checked on the phone and the server, and a pallet taken off frees its number. Each line records its `block_id` (optional, picked from the blocks in `Store.sources()`, the sulfur screen's fruit received today and the last earlier receiving day, so "yesterday" is really the last earlier receiving day; a new line starts on the block above), and the pallet its `date_code` (suggest.js `dateCode` of the day scanned, kept as scanned). Tapping a pallet opens it to change or delete; each pack line has a delete button. The server still gives each pallet its `pallet_year`/`pallet_no` (0001 each year, farm-local) the first time it arrives and never changes it (no longer shown; `pallet_year` is the season); a removed pallet keeps its number but frees its barcode, which is otherwise unique. There is no consignment number yet (the date stands in), no traceability to runs or lots, and Delivery Note is a separate role.
- **Delivery Note** (`frontend/deliverynote.js`, `routers/delivery_note.py`, `routers/delivery_settings.py`): the paper Afleweringsnota, made on a phone at `#deliverynote` (its settings at `#settings/deliverynote`), with the same badge scan or PIN and `Operator`. The screen is New delivery note (saving a note, new or edited, comes back here; tap it to print or share it), then Delivery notes added today (made on this phone's day, and any refused one) and Earlier delivery notes (every other note the phone holds, 90 days, greyed but still tapped to edit, print or delete), each under a heading per market group (USA, EU, Local; `noteGroup`), each showing its market (its pallets' market names, `noteMarkets`), as the note's own page does under its title. A note is its `note_no` (typed on the first note, carrying on from the paper book; every new note then offers the last note number + 1: `DeliveryNoteSettings.last_no`, which moves up by itself as notes arrive and Settings -> Delivery Note can set, down too, to carry on from the paper book or undo a typo; cleared, the highest note ever; served as `last_no` by `/options`, since the phones only hold 90 days; unique among live notes, a deleted one frees it), the receiver and transporter (picked from Settings -> Delivery Note: `Receiver` is name, market, Address 1, Address 2 and city, copied onto the note one per line (a note copied with only the name prints the market, address and city from Settings, `_live` in the router); `Transporter` is a name; both seeded from the paper notes, retired by unticking In use, deleted only while no live note uses one; both listed A to Z by name, capitals or not), seal no (typed or scanned, Html5Qrcode as for a pallet label), cooled to (°C, starting at `DeliveryNoteSettings.cooled_to`, 8), the load and offload dates (farm-local `YYYY-MM-DD`; the offload date starts as the day after the load date and follows it until changed by hand) and **the pallets in this delivery**: ticked off the Pallet Stack list (every pallet on no other live note, newest first), each shown as Pallet Stack shows it (`palletSummary` in consignment.js), under a heading per market group, USA, EU and Local (`marketGroup`: the word USA or EU in the market name, else local). **A note holds one group**: once a pallet is ticked the other groups are greyed out, and the server refuses a mixed note (`export_forms.market_group`). A pallet is on at most one live note. **Deleting a note wants the settings PIN** (`askPin` in app.js, the keypad with a Cancel, checked by `/api/admin/check`; a gate on the phone only, the sync endpoint stays open), and frees its pallets. The note keeps its own copy of each pallet (number, barcode, date code, supplier, market, lines), which the server takes from its own `Pallet` when the note is saved, so a pallet edited afterwards leaves a note that has gone out as it was; the phone only needs to send the uuids. Kind `delivery_note` goes through the same outbox to `POST /api/deliverynote/sync`, after the pallets (a note whose pallet has not reached the server is refused until saved again), editable like a pallet (`rev`, latest copy wins, `made_by` set once); `GET /api/deliverynote/options` gives the phones the receivers, transporters and cooled-to. **Only a local note prints this note** (B-, the Bekfontein Afleweringsnota): a USA or EU note goes out on its market's documents instead (below), its page showing that button in place of this one, and the PDF answers 409 for it. **Print or share** fetches `GET /api/deliverynote/{uuid}/pdf` (fpdf2, A4, laid out as the paper note with the farm's printed details in the router and the signature boxes blank; every printed label in Afrikaans with the English beside it (AFLEWERINGSNOTA / DELIVERY NOTE), the small print in both; one style throughout, the receiver in capitals like the sender, the three signature boxes and Transporter | Seel nr | Verkoel op in equal thirds; instead of Getal, a Pallet no column with each pallet a block of its own, shown as Pallet Stack shows it, then a total of pallets, cartons and kg, the dates, and the small print last, all boxed on under it; every page has "page X of Y" in red beside the note number, and a block that won't fit starts a new page with the same title line; `_draw` draws the note once to count its pages, then again with the count) and hands it to the phone's share sheet (WhatsApp, print), else downloads it; the server makes it, so a note still in the outbox has to be sent first. **The note's number is printed with a prefix:** `LW-1335` when it carries an export (USA or EU) pallet, `B-1335` otherwise (local); a juice note has its own series, `J-0001` on; one series of numbers, only `note_no` stored, the prefix worked out from the pallets' market names (`export_forms.note_label`, `noteLabel` in deliverynote.js) on the screens, the PDF and the file names. A USA or EU note has its market's papers instead of the delivery note (`backend/export_forms.py`; the market is read off the pallets' market names, the word USA or EU, `exportButtons` in deliverynote.js; `MARKETS` in the router): **USA forms** are DAFF's phyto accompanying document, the consignment note and PPECB's litchi inspection findings sheet; **EU forms** are the same without the phyto document, with EU as the target market. One row per pallet line. `GET /api/deliverynote/{uuid}/{usa|eu}_forms.xlsx` draws them as the paper forms in one style (Arial, labels bold on grey, every block boxed, A4 portrait fitted to the width, the DALRRD logo from `backend/templates/`); `{usa|eu}_forms.pdf` is the same workbook drawn as one PDF by `export_forms.forms_pdf` (fpdf2, each sheet fitted to the A4 width, long ones carried on with their header row; the phone has an Excel and a PDF button per market), the Phyto form on one page (at least 13 ruled pallet rows, more lines more rows, the page fitted to its height with the gaps between blocks kept small so the rows stay big enough to write in), the consignment note with PUC, PHC and GGN under Sender, then "GlobalG.A.P. Certified" under the GGN, and the note's **target receiver** in the Consignment block. Target receivers are a list in Settings -> Delivery Note like the receivers (`TargetReceiver`: name, address, market USA or EU, In use; served by `/options` as `target_receivers`); a USA or EU note picks one of its market's (the box shows once its first pallet is ticked) and copies it (`target_receiver_id`, `target_receiver`, name and address one per line); a local note has none, cleared by the server. Pallet ID is the barcode without `(00)`, Count is the size word in the pack's name (`Rhino 4.5 kg XL`), the document number the note's label; the exporter (AgriLink) and the farm's PUC, PHC, inspection point and GGN are constants in `export_forms.py`. To see a sheet without Excel: `qlmanage -t -s 1400 -o <dir> <file>.xlsx` renders its first sheet (Quick Look skips a picture without a two-cell anchor and its own size, hence the logo's).
- **Juice** (`frontend/juice.js`, `routers/juice.py`, icon a litchi, `LITCHI` in app.js): the juice bins and crates, made on a phone at `#juice` with the same badge scan or PIN and `Operator`, replacing the paper weigh sheet with the scale's two stickers per bin. A bin or crate (`JuiceBin`, `container` "bin" or "crate"; "bin" in the code means either) is its `bin_no` (offered as the highest this season + 1, bins and crates numbered apart, unique among the season's live ones of its kind, `bin_year` set once), `empty_kg` and `full_kg` (a crate record is a batch, counted not weighed: Batch no, Number of crates in batch (`count`) and Weight / crate (`full_kg`, no empty weight), Total weight = count × weight per crate, the net; one from before batches keeps its empty weight and stays full − empty; a bin's count is 1): weighed empty first and saved, then opened again when full (either weight may wait; a bin on a note needs both). The screen is New bin and New crate, then New Juice Delivery Note, then Bins and crates weighed today (and any still waiting for a weight or refused, whatever its day), each as Bin 88 or Crate 3 (`binName`), full − empty = net (`binSummary`). Kind `juice_bin` goes through the same outbox to `POST /api/juice/sync`, before the notes, editable like a pallet (`rev`, latest copy wins, `made_by` set once). The list puts bins still waiting for a weight first, then the full ones in green; in each part bins, then crates, highest number first. Full bins go on a **juice delivery note**, made with the Juice screen's New Juice Delivery Note (`openNote(null, true)`, on the Delivery Note screen): it offers only the full bins and crates on no other live note (one waiting for a weight is never listed, and the server refuses it) (the Juice group, orange, in `MARKET_GROUPS`), has no seal no or cooled to, starts with the receiver and transporter of the last juice note. The Juice screen ends with its own Delivery Notes list of the juice notes (`juiceNotesView`: today's, then earlier ones greyed); a juice note opened from Juice (`dn.from`) goes back there when saved, deleted or left (`leaveNote`). The Delivery Note screen's own New delivery note offers only pallets; a note holds pallets or bins, never both (the server refuses it). The note keeps its own copy of each (`DeliveryNote.bins`: uuid, container, number, empty and full kg; bins, then crates, in number order), has its own number series from `J-0001` (unique among live juice notes; `/options` sends `last_juice_no`, its highest live one; `DeliveryNoteSettings.last_no` is the B-/LW- series only; `note_label`/`noteLabel` pad it to 4 digits), is coloured in the notes lists by what it holds (`juiceRowKey`: bins orange, crates yellow, both rose), prints with Houer / No (Bin 88, Crate 1) | full − empty = net and the total (1 bin · 1 crate · 476 kg), and has no target receiver. A bin on a live note can't be deleted or lose a weight on the phone. The empty bins coming in (Palogix) and Onderberg's figures are stages B and C in the plan, not built.
- **Sync rules both modules share** (`frontend/sync.js`, `routers/sulfur.py`, `routers/acid.py`): each module's endpoint is sent on its own, so one that errors never holds the other back. A record the server refuses is kept in IndexedDB with its error but never shown. Stages move forward in one place, `sulfur.advance` (a run's `ended_at`; a batch's `dip_ended_at` then `ended_at`): the first time sent stands, and one that arrives ending before the stage before it (two tablets' clocks a little apart) is clamped to that earlier time, never refused, because refusing would leave it running on the server for ever. `Store`'s localStorage copies are parsed once and kept in memory (`cached`/`keep`); treat them as read-only. Records for a retired tent or bath are accepted: the work happened.
- **Aril SO₂ estimate** (`estimateResidue` in `suggest.js`): shown live on each tent card against the EU limit of 10 ppm SO₂ in the aril (amber from 8, red from 10). No published model predicts aril residue, so it is anchored to one residue at the reference load (`residue_ref_ppm`, 5 ppm to start, the farm's choice) and scaled by chosen time ÷ unrounded suggested time, because the suggestion is built to hold residue at that anchor. The card says "Not calibrated" until a lab result (Monier-Williams) is entered and ticked in Settings -> Sulfur (`residue_calibrated`). It does not model the acid dip, ripeness or overnight holding, which all raise residue. Each run stores `estimated_ppm`, for comparing with lab results.
- **Frontend:** a single vanilla-JS PWA, no build step. `frontend/shared/` (api.js, sw-core.js, styles.css, tailwind.js, vendor/) is vendored from Boord via Labour. Only `VERSION` in api.js is ours. Bump `CACHE` in `service-worker.js` when shell files change. An inline script at the top of `index.html` reloads the page once when a new release's service worker takes over a running page (`controllerchange`): Boord's `sw-core.js` uses `skipWaiting` + `clients.claim`, so without it a page could load the old `index.html` and the new `app.js` (v0.11's empty Setup page).
- **Icon:** Boord's crate with an orange leaf (`#fb923c`), rendered with `../Boord/scripts/render_icons.py`'s `render()`.
- **Deployment files** (`install.ps1`, `install.bat`, `update_packhouse_server.bat`, `stop_server.ps1`, `scripts/release.sh`) are adapted from Boord Labour's. Keep fixes flowing between the sibling repos. `tests/test_updater.py` keeps the updater's import check equal to `requirements.txt`.

## Installing and deploying

### Where it lives

| | |
|---|---|
| Your Mac (the only clone to release from) | `~/Documents/Projects/Boord-packhouse` |
| Farm PC folder | `C:\Boord-packhouse` |
| Farm PC scheduled task | "Boord Packhouse Server", runs as SYSTEM at boot |
| Port on the farm PC | `127.0.0.1:8060` |
| Address on the tailnet | `https://bekfontein-server.taile32cb0.ts.net:8060/` |

### First install on the farm PC (once)

Only for a new PC or a reinstall. An app that is already running is updated, not reinstalled.

1. Open a Command Prompt and clone the repo into the folder above:
   ```bat
   git clone https://github.com/DawiePieterse/boord-packhouse.git C:\Boord-packhouse
   ```
2. In `C:\Boord-packhouse`, double-click **`install.bat`** and accept the administrator prompt. It asks for the full path to Boord's `data\boord.db`.
   It installs Python if needed, builds the app's environment, writes the launcher, registers the scheduled task, reserves the port so Windows can't hand it to Hyper-V, WSL or Docker at boot, and starts the server. Re-running it is safe and keeps the data.
3. Tell the updater which release key to trust. In the same folder, type it exactly like this, with the redirect first:
   ```bat
   >data\release_key.fpr echo 67C64CFDD584DD140E58AF6E329C9B9DD0562A9D
   ```
4. Publish it on the tailnet, in a Command Prompt opened as administrator:
   ```bat
   tailscale serve --bg --https=8060 http://localhost:8060
   ```
5. If the installer did not already add it, let SYSTEM's Git read the folder, as administrator (forward slashes):
   ```bat
   git config --system --add safe.directory C:/Boord-packhouse
   ```
6. Check it from your Mac: `curl -s https://bekfontein-server.taile32cb0.ts.net:8060/api/version` should show the release tag.

### Deploying a change (every release)

Merging to `main` changes nothing on the farm. A release is a signed tag, and the farm PC installs it when its updater runs.

1. **Merge the PR on GitHub.** A frontend change must already bump `VERSION` in `frontend/shared/api.js` and the service worker's `CACHE`.
2. **On your Mac, bring the clone up to date.** This step is what stops a tag landing on an old commit:
   ```sh
   cd ~/Documents/Projects/Boord-packhouse && git checkout main && git pull --ff-only origin main
   git log -1 --format='%h %s'                  # the merge you expect
   grep -m1 'VERSION:' frontend/shared/api.js   # the version you are releasing
   ```
3. **Sign and push the tag** (`vX.Y` must equal `VERSION`):
   ```sh
   scripts/release.sh vX.Y && git push origin vX.Y
   ```
   Never move or reuse a released tag. Fix a wrong one with the next version.
4. **On the farm PC**, in `C:\Boord-packhouse`, double-click **`update_packhouse_server.bat`**. It verifies the signature, stops the server with `stop_server.ps1`, installs dependencies, copies and migrates the database, and starts it again. If it stops with an error, nothing has changed. Read the message; never check the tag out by hand.
5. **If the release changed `install.ps1`** (its notes say "run install.bat once more"), double-click `install.bat` as well. The updater does not rewrite the launcher or the task.
6. **Check from your Mac:** `curl -s https://bekfontein-server.taile32cb0.ts.net:8060/api/version` should show `"tag":"vX.Y","state":"release"`.
7. **Close and reopen the app on each tablet so they load the new version.**
